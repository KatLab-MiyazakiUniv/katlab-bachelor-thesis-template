\chapter{研究の準備}\label{cha:Preparation}

本章では、本研究で提案するプロンプト作成手法の基礎となる技術的要素、および実験の基準となるシステム仕様書について述べる。

\section{Large Language Models (LLM)}
\label{sec:llm}

大規模言語モデル（Large Language Models: LLM）は、大量のテキストデータを学習し、人間のような自然な文章を生成したり、質問に応答したりすることができる人工知能モデルである\cite{llm_survey}。
LLMは、Transformerと呼ばれるニューラルネットワークアーキテクチャを基盤としており、文脈理解、文章要約、翻訳、コード生成など、多岐にわたるタスクを高い精度で実行可能である。
従来の自然言語処理手法と比較して、LLMは明示的な学習データを与えなくても、プロンプト（指示文）による制御のみで多様なタスクに対応できる「Zero-shot」や「Few-shot」の能力に優れている点が特徴である。

本研究では、OpenAI社が提供する対話型AIサービスであるChatGPT、その中でも特に高度な推論能力と指示追従能力を持つモデルである\textbf{ChatGPT 5.2}を用いた。
ChatGPT 5.2は、複雑な文脈の理解や、長文の生成において優れた性能を示しており、システム仕様書のような構造的かつ整合性が求められるドキュメントの生成に適していると考えられる。

\section{プロンプトエンジニアリング}
\label{sec:prompt_engineering}

プロンプトエンジニアリングとは、LLMから望ましい出力を得るために、入力する指示文（プロンプト）を設計・最適化する技術のことである。
LLMの性能を最大限に引き出すためには、モデルの特性を理解し、適切な指示を与える必要がある。以下に、本研究に関連する主要な手法について述べる。

\subsection{Zero-shot / Few-shot Learning}
\label{subsec:zero_few_shot}

Zero-shot Learningは、モデルに対してタスクの具体的な回答例（Example）を与えずに、指示のみでタスクを実行させる手法である。
一方、Few-shot Learningは、いくつかの入出力ペア（例題）を提示することで、モデルにタスクの実行方法を学習させる手法である。
一般に、Few-shot Learningの方が精度が高いとされるが、タスクが複雑すぎる場合や、例題の作成が困難な場合はZero-shot Learningが用いられる。

本研究では、作成するシステム仕様書章立てのためのプロンプトがあらゆるシステムに対応できる汎用性を持つ必要があるため、特定のシステムに依存した「正解の章立て例」を与えることが困難である。
そのため、基本的には\textbf{Zero-shot Prompting}の手法を採用している。
ただし、出力形式（フォーマット）に関しては、LLMが安定して出力できるように、フォーマットの例を1つ提示するアプローチ（One-shot Prompting）を取り入れている。

\subsection{Chain of Thought (CoT)}
\label{subsec:cot}

Chain of Thought (CoT) は、モデルに対して「段階的に考えさせる」ことで、複雑な推論タスクの精度を向上させる手法である\cite{cot}。
答えを直接出力させるのではなく、思考過程を出力させることで、論理的な整合性を保ちやすくなる。

本研究では、このCoTの概念を応用し、システム仕様書の作成という複雑なタスクを、以下の2段階に分解して実行させている。
\begin{enumerate}
    \item 骨子となる「章立てのみ」を作成する（構造の決定）
    \item その章立てに基づいて「各項目の説明」を作成する（詳細の記述）
\end{enumerate}
このように、一度に全てを出力させるのではなく、構造決定から詳細記述へと段階を踏ませることで、論理の飛躍や記述の矛盾を防ぐ設計としている。

\section{プロンプトデザインパターン}
\label{sec:prompt_patterns}

プロンプトデザインパターンとは、プロンプトエンジニアリングにおける知見をパターン化し、再利用可能な形に体系化したものである。
本研究で作成したプロンプトでは、Jules Whiteらが提案するプロンプトパターンカタログ\cite{prompt-engineering}を参考に、以下のパターンを適用した。

\subsection{Persona Pattern}
\label{subsec:persona_pattern}

Persona Pattern（ペルソナパターン）は、LLMに対して特定の役割（ペルソナ）を与えることで、その役割に適した振る舞いや回答を促すパターンである。
例えば、「あなたは教師です」と指示すれば、解説調の丁寧な回答が得られやすくなる。
本研究では、プロンプトの冒頭で「あなたはシステム仕様書作成の専門アシスタントです」と役割を定義することで、専門的かつ実務的な章立ての出力を誘導している。

\subsection{Template Pattern}
\label{subsec:template_pattern}

Template Pattern（テンプレートパターン）は、LLMに対して出力の形式を具体的かつ厳密に指定するパターンである。
LLMは自然言語で自由な回答を生成する傾向があるため、後続のプログラムで処理したり、人間が比較検討したりするためには、出力形式の統一が不可欠である。
本研究では、マークダウン形式の番号付きリストや、特定の区切り文字の使用を強制することで、可読性と再利用性の高い出力を実現している。

\subsection{Context Manager Pattern}
\label{subsec:context_manager_pattern}

Context Manager Pattern（コンテキストマネージャパターン）は、LLMに対して考慮すべき情報の範囲（コンテキスト）を明示的に指定、あるいは除外することで、生成内容の焦点や関連性を制御するパターンである。

LLMは、対話の履歴や曖昧な指示に含まれる無関係な情報に影響され、意図しない回答を生成する場合がある。
これに対し、本パターンでは以下のような明示的な指示（Contextual Statements）を与えることで、LLMの思考の範囲を制御する。

\begin{itemize}
    \item \textbf{範囲の指定 (Within scope X)}: 特定のトピックや条件下でのみ回答するように制限する。
    \item \textbf{考慮事項の指定 (Please consider Y)}: 重要な概念や事実を明示し、それに基づいた回答を促す。
    \item \textbf{除外事項の指定 (Please ignore Z)}: フォーマットや特定のトピックなど、考慮すべきでない要素を明示的に排除する。
\end{itemize}

本研究では、システム仕様書の生成において、対象とするシステムの具体的な情報（考慮事項）を与えたり、記述すべき仕様の粒度や範囲（除外事項）を厳密に定義したりするために、このパターンの概念を適用している。

\section{システム仕様書}
\label{sec:system_spec}

\subsection{本研究におけるシステム仕様書の位置づけ}
\label{subsec:system_spec_position}

一般にソフトウェア開発においては、顧客の要望をまとめた「要件定義書」から始まり、それをシステムとしてどのように実現するかを定義する「設計」フェーズ、そして具体的なコードに落とし込む「実装」フェーズへと進む。
本研究において取り扱う「システム仕様書」は、この開発プロセスの中で、上流の「要件定義」と下流の「プログラム設計（詳細設計）」の中間に位置するドキュメントと定義する。

具体的には、株式会社スカイコムにおける開発プロセスをモデルとし、以下の3段階のドキュメント構成を前提とする。

\begin{enumerate}
  \item \textbf{要件定義書}: 顧客の要望が記載された文書。機能や要望が定性的に書かれており、粒度は粗い。
  \item \textbf{システム仕様書（本研究の対象）}: 要件定義書の内容をシステム的な観点でブレイクダウンし、実装者が「何を作るべきか」を理解するための文書。
  \item \textbf{プログラム設計書}: システム仕様書を実現するために、具体的に「どう作るか」を記述した文書。使用するクラス、メソッド、処理手順などの内部構造が含まれる。
\end{enumerate}

すなわち、本研究におけるシステム仕様書は、一般的な「外部設計書」や「基本設計書」に相当する。
このドキュメントは、以下の2つの目的を達成するために作成される。

\begin{itemize}
  \item \textbf{実装者（プログラマ）への指針}:
  新人プログラマであっても、仕様書を読み込むことでシステムの挙動を正しく理解し、迷いなく設計・実装に着手できること。
  \item \textbf{テスト担当者への基準}:
  システムの内部構造（コード）を知らないテスト担当者が、仕様書に記載された正常系・異常系の条件に従って、ブラックボックステストの項目を作成できること。
\end{itemize}

したがって、記述スタイルとしては、専門用語や初出単語の丁寧な説明が求められ、特にシステムの概要や振る舞いについては、テキストだけでなく図（ユースケース図や簡易図）を用いて視覚的に説明することが不可欠である。
また、記述の粒度としては、画面レイアウトや操作フローといった「外部仕様（ユーザーから見える振る舞い）」に焦点を当て、データ型や制約条件は網羅するものの、クラス図や具体的なアルゴリズムといった「内部仕様」は含まないこととする。


\subsection{一般的なシステム仕様書の構成}
\label{subsec:general_spec}

システム仕様書の構成は、プロジェクトの特性や組織の標準により異なるが、一般的に「外部設計書」や「基本設計書」として作成される文書には、システムが提供する機能や振る舞いを網羅的に記述することが求められる。
国際的な標準としては、IEEE 830 (Recommended Practice for Software Requirements Specifications)\cite{ieee830} が広く知られており、機能要件、外部インターフェース、パフォーマンスなどの非機能要件を記述することが推奨されている。

これらを踏まえ、一般的なシステム仕様書（外部設計書）は、主に以下の要素で構成されることが多い。

\begin{enumerate}
    \item \textbf{システム概要}: システムの目的、背景、全体像（コンテキスト図など）。
    \item \textbf{機能要件}: システムが提供する機能の一覧と、各機能の詳細な振る舞い（入力・処理・出力）。
    \item \textbf{ユーザーインターフェース (UI)}: 画面レイアウト、画面遷移図、操作フロー。
    \item \textbf{データ要件}: 扱うデータの定義（ER図やデータディクショナリ）。
    \item \textbf{外部インターフェース}: 外部システムとの連携仕様、API定義。
    \item \textbf{非機能要件}: セキュリティ、性能、信頼性、制約事項など。
\end{enumerate}

本研究で対象とするシステム仕様書も、これらの標準的な構成要素を網羅しつつ、実装者が迷わずに開発を行える粒度での記述を目指している。
